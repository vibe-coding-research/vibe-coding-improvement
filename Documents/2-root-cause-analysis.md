# 문제의 원인 분석
> AI 생성 코드의 계보 기반 신뢰 추적 시스템 — 바이브 코딩 AI 개선 아이디어 공모전

---

## 1) AI 역량의 비대칭성: 생산 속도와 맥락 이해의 간극

바이브 코딩 문제의 출발점은 AI가 가진 능력의 불균형에 있다. AI는 수조 개의 데이터를 학습해 언어와 프레임워크를 가리지 않고 즉시 코드를 생성하며, 인간이 소요하던 시간을 초 단위로 단축했다.

그러나 이 압도적인 생산성 뒤에는 결정적인 한계가 있다. AI는 사용자가 제공한 프롬프트라는 좁은 틀 안에서만 사고한다. 실제 서비스의 복잡한 비즈니스 로직, 숨겨진 예외 상황, 시스템 전체 맥락을 스스로 파악하고 논리적으로 완결 짓는 능력은 여전히 인간의 영역이다.

결과적으로 개발자는 AI의 빠른 속도에 이끌려, 논리적 결함을 검토하기도 전에 코드를 시스템에 통합하게 된다.

> **속도가 검증을 앞질러 버리는 구조다.**

---

## 2) 사고 과정의 소멸: 결과만 있고 이유가 없는 코드

기존 개발 방식에서 코드는 단순한 결과물이 아니었다. 개발자가 고민한 흔적이 주석으로, 시행착오가 커밋 메시지로, 판단의 근거가 코드 리뷰로 남았다. **코드 자체가 하나의 문서였다.**

바이브 코딩은 이 구조를 해체한다.

AI는 최종 코드 블록만 던질 뿐, 왜 이 방식을 선택했는지, 어떤 보안 요소를 고려했는지, 어떤 대안을 검토하고 버렸는지에 대한 추론 과정은 블랙박스 안에 사라진다. 코드가 수정될 때 누가 왜 바꿨는지에 대한 인과관계가 끊어지면서, 유지보수 시 코드를 해석할 단서 자체가 존재하지 않게 된다.

---

## 3) 기존 도구의 구조적 한계: 상태를 보지만 계보를 보지 못한다

현재의 정적 분석 도구와 Git은 코드의 현재 상태(Snapshot)를 진단하는 데 최적화되어 있다. 그러나 바이브 코딩 환경이 요구하는 것은 코드의 생애 주기(Lineage)를 거슬러 올라가는 추적 능력이다.

### 기존 도구가 답하지 못하는 질문들

- 이 코드는 AI가 만들었는가, 사람이 만들었는가?
- 어떤 프롬프트에서 시작되었는가?
- 이 취약점은 몇 주 전 어떤 세션에서 유입되었는가?
- 코드가 수정된 이유와 검토 이력은 어디에 있는가?

### 기존 도구 vs 새로운 요구사항

| 관점 | 기존 정적 분석 / Git | 바이브 코딩 환경의 요구사항 |
|---|---|---|
| **분석 시각** | Snapshot (현재 상태) | Lineage (생애 주기) |
| **분석 내용** | 구문 오류, 스타일 체크, 변경 이력 | 코드 출처, 생성 의도(Prompt), 모델 신뢰도 |
| **한계** | 코드가 어떻게 생성되었는지 알 수 없음 | 코드의 뿌리부터 신뢰 문제 해결 가능 |

---

## 4) 검증 체계의 부재: 실행 성공이 품질 보증은 아니다

바이브 코딩 환경에서 가장 위험한 착각은 **에러 없이 실행되는 코드를 좋은 코드로 간주하는 것**이다.

AI는 동작하는 코드를 생성하는 데 최적화되어 있지만, 그 코드가 보안상 안전한지, 예외 상황에 강건한지, 자원을 효율적으로 사용하는지에 대해서는 보장하지 않는다.

이를 독립적으로 검증할 자동화 레이어가 존재하지 않아, 개발자는 AI의 결과물을 사실상 필터링 없이 수용하게 된다. 잠재적 위험은 코드베이스 깊숙이 누적되고, 장애나 보안 사고가 발생했을 때 비로소 문제가 드러나지만 그때는 이미 원인을 추적하기 어려운 상태가 되어 있다.

| **검증 체계의 부재** | 독립적 자동화 검증 레이어 없음 | 잠재 위험이 배포 후에야 발견됨 |
