# 문제 정의
> AI 생성 코드의 계보 기반 신뢰 추적 시스템 — 바이브 코딩 AI 개선 아이디어 공모전

---

## 1. 배경

생성형 AI의 급속한 발전은 소프트웨어 개발의 진입 장벽을 근본적으로 낮추고 있다. OpenAI의 ChatGPT, Anthropic의 Claude, GitHub Copilot과 같은 도구들은 전문적인 개발 지식 없이도 누구나 즉시 코드를 생성할 수 있는 환경을 만들었다. 이른바 **'바이브 코딩(Vibe Coding)'** 의 시대다.

코딩은 쉬워졌고, 속도는 빨라졌다. 그러나 이 편리함의 이면에서 우리는 점점 중요한 질문들을 잊어가고 있다.

> **"이 코드는 어디서 왔는가? 왜 이렇게 작성되었는가? 그리고 이 코드를 신뢰할 수 있는가?"**

속도와 생산성이라는 단기적 이득 뒤에, 우리가 운영하는 시스템의 기반이 서서히 흔들리고 있다.

---

## 2. 핵심 문제

### 2-1. 바이브 코딩이 만들어내는 블랙박스: '기술적 실독증'의 양산

LLM 에이전트 기반 바이브 코딩이 주류 개발 방식으로 자리 잡으면서, 개발자는 코드의 세부 구현 원리를 알지 못한 채 결과물을 서비스에 반영하는 일이 일상화되었다. 이 구조는 세 가지 치명적인 단절을 만들어낸다.

**첫째, 코드 이해의 단절이다.**
사용자는 AI가 생성한 코드의 실행 여부만 확인할 뿐, 내부 로직의 흐름이나 설계 의도를 파악하지 못한다. 이는 개발자가 자신이 운영하는 시스템의 작동 원리를 이해하지 못하는 **'기술적 실독증(Technical Illiteracy)'** 상태를 유발한다.

**둘째, 검증 없는 수용이다.**
AI는 사용자의 프롬프트라는 좁은 맥락 안에서만 사고하며, 할루시네이션으로 인해 겉보기에는 완벽하지만 내부적으로 심각한 결함을 포함한 코드를 제안할 수 있다. 검증 능력이 결여된 상태에서 이러한 코드가 서비스에 반영되는 순간, 시스템 전체의 신뢰도가 무너지는 것은 시간문제다.

**셋째, 이력과 책임의 상실이다.**
기존의 버전 관리 시스템(Git)은 코드의 변경 사항을 기록하지만, 해당 코드가 어떤 의도(Prompt)로 생성되었는지, AI와 인간 중 누구의 판단이 개입되었는지에 대한 계보는 추적하지 못한다. 코드는 남지만 맥락은 사라진다.

---

### 2-2. 소프트웨어 생애 주기 전반에 걸친 구체적 위험

블랙박스 코드가 시스템에 누적될수록 그 피해는 소프트웨어 전체 생애에 걸쳐 복리로 증가한다.

| 구분 | 주요 영향 및 발생 가능한 시나리오 |
|---|---|
| **품질 (Quality)** | AI는 프로젝트 전체 아키텍처보다 로컬 로직 최적화에 집중한다. 기존 코드 컨벤션과 충돌하거나 중복된 로직이 반복 생성되면서 소프트웨어의 구조적 품질이 서서히 하락한다. |
| **안정성 (Stability)** | AI는 사용자가 명시하지 않은 예외 상황(네트워크 지연, 비정상 입력 등)을 생략하는 경향이 있다. 개발자가 이를 인지하지 못한 채 배포하면 특정 조건에서 시스템이 예기치 않게 중단된다. |
| **보안 (Security)** | 학습 데이터에 포함된 구시대적 보안 패턴이나 취약한 라이브러리 로직이 필터링 없이 삽입될 수 있다. 코드를 해석하지 못하는 개발자는 보안 사고가 발생하기 전까지 위험을 인지조차 하지 못한다. |
| **유지보수 (Maintenance)** | 장애 발생 시 코드를 작성한 주체와 당시의 맥락을 알 수 없어 원인 파악에 과도한 시간이 소요된다. 결국 '무서워서 건드리지 못하는 코드'가 누적되며 시스템 전체가 거대한 레거시 덩어리로 굳어간다. |

---

### 2-3. 문제의 본질: 신뢰의 패러다임이 바뀌어야 한다

소프트웨어 개발에서 신뢰는 오랫동안 '이해'에 기반해 왔다. 개발자가 코드를 직접 작성하고, 동료가 리뷰하고, 주석과 커밋 메시지로 의도를 남기는 일련의 과정이 신뢰의 근거였다.

그러나 AI가 코드의 상당 부분을 생성하는 바이브 코딩 시대에는 이 전제가 무너진다. AI가 코드를 생산하는 속도와 인간이 그것을 검증하는 속도 사이의 간극은 점점 벌어지고 있다.

코드를 이해하지 못해도 개발은 가능하다.
그러나 코드의 출처와 맥락을 추적하지 못하면, **신뢰는 불가능하다.**

> 이제 소프트웨어 개발의 신뢰 근거는 **'이해'에서 '검증과 추적'으로** 이동해야 한다.
